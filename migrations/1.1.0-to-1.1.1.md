# 1.1.0 → 1.1.1

首个正式发布批次。`v1.1.1` 是第一个 tag；不把仓库里多个 `1.1.0` 提交追认成同一正式 tag。

`1.1.0` 至少有两套可核实命名，以及工作区已经落地的待办/实施调整。必须按目录和 Skill 文件识别，不能因 manifest 写着 `1.1.0` 就推断用了哪一套。

从 `1.0.0` 直达 `1.1.1` 时先读完 [1.0.0 → 1.1.0](./1.0.0-to-1.1.0.md)，再读本文；中间已被覆盖的改动按本文最终态一次做完。

## why

1. 意图 Skill 从 `capture/plan/abandon` 改名为 `new/impl/drop`。
2. 意图生命周期从单一 `进行中/` 拆成 `待办/` 与 `实施/`；旧 `进行中/` 只按需兼容。
3. 把 `https://github.com/chenweixuanJokes/ph-init.git` 定为唯一正式源；Init 先准备发行版再跑离线内核。
4. 新增 `ph-merge-update`，已安装项目走合并升级，不再用 `init --apply` 覆盖。
5. Schema 与发布版本改为独立维护；本批契约从九 Skill / `1.1.0` 锁变为十 Skill / `1.1.1`，因此 Schema 也是 `1.1.1`。
6. 更新项目内 PH 分发材料与混合文档中的 Skill / 升级入口，保留项目正文事实。

## from

用实态判定起点，下列布局都算合法 `1.1.0` 历史：

| 实态 | Skill | 意图目录 | 版本锁 |
| --- | --- | --- | --- |
| 旧命名九 Skill | `ph-intent-capture` `ph-intent-plan` `ph-intent-abandon` | 通常仍是 `进行中/` | `1.1.0` |
| 新命名九 Skill | `ph-intent-new` `ph-intent-impl` `ph-intent-drop` | 可能仍是 `进行中/` | `1.1.0` |
| 已提前改待办/实施 | 多为新命名九 Skill | 已有 `待办/` `实施/`，可能仍留 `进行中/` 业务条目 | 仍可能是 `1.1.0` |

`1.0.0` 六 Skill 不是本文的 from；应先走 `intent-domain`。未知布局或缺迁移记录则阻断。

## to

- 十个必需 Skill，意图名为 `ph-intent-new` / `ph-intent-impl` / `ph-intent-drop`，另加 `ph-merge-update`。
- 导航与规则使用 `docs/意图/待办/{新特性,问题记录}/` 与 `docs/意图/实施/{新特性,问题记录}/`。旧 `进行中/` 保留业务条目，不批量改派。
- Init：`ph_release.py prepare` 取固定 tag/commit，再跑该 commit 的 `ph_init.py`。`check` / `sync` 用项目已装内核，不访问网络，不在目标仓库 `git pull`。
- 已安装项目：`ph_merge_update.py inspect` 只读 → Agent 按本文合并 → `verify` → `finalize` 在 candidate check 通过后才写版本。
- `schema_version` 与 `template_version` 目标均为 `1.1.1`，但含义独立；以后只改 Skill/文档不必自动升 Schema。
- 项目进度写在 `.agents/updates/1.1.1/state.json` 与 `report.md`。

- `.agents/ph.json` 的 `required_names`、`.agents/AGENTS.md` Skill 表、工程规范/意图 README 中的旧名字。
- `.claude/skills`、`.codex/skills` 里对应旧名入口：审阅后退役，先备份。
- 已是 `new/impl/drop` 则本项 `not_applicable`。

### intent-lifecycle

- 新建 `docs/意图/待办/`、`docs/意图/实施/` 及两组 `新特性/` `问题记录/` 和 README。
- 更新 `.agents/AGENTS.md` 文档导航、`docs/意图/README.md`、文档治理与意图与访谈中的**目录表/导航**；不重写意图业务正文。
- 已存在待办/实施（含本仓库工作区这种提前落地）则补缺目录与索引，本项可部分 `applied`。
- 旧 `进行中/` **不**批量移动、不按标题猜测已完成或待办。

### online-source

- 项目内 `ph-init` 的 `SKILL.md` 改为：正式 Init 先 `prepare`，再读准备根的 SKILL 并执行该根 `ph_init.py`。若项目另有安装说明则一并合并，不要求安装包携带仓级 README。

### merge-update

### schema-contract

### project-content

- 混合文件（AGENTS 项目区、规范占位、README）按段落合并：更新 PH 入口与 Skill 计数，保留已填事实。
- 业务意图、纪要、Wiki、记忆：仅当某项明确要求时才改（通常只是索引链接）。
- 用准备根更新项目内 `ph-init` payload，保留该副本上的项目定制。

## preserve

- 访谈原话、历史代码块、业务编号、无关 Wiki 与记忆。
- 旧 `进行中/` 里的业务条目与有效引用；`new` 补充保持原位，只有用户对单条调用 `impl` / `drop` 才移动。
- adapter mode、用户显式规则、已填的 `<填写：…>` 之外的项目事实。
- 旧 Skill 若有本地定制：审阅备份，不静默删除。

## conflict

- 项目显式规则与目标模板相反：该项 `blocked`，停止受影响写入，请用户决定。
- 旧 Skill / 厂商入口内容与模板不同：备份到受控目录或 `~/trash/`，不 `rm`；冲突未决不退役。
- 根 AGENTS 与 canonical 迁移关系不成立、仓外软链、嵌套 symlink/junction、受跟踪 `.worktrees/`：沿用 init 的 fail-closed。
- 重复执行或中断恢复：对照 `state.json` 与文件实态，已落地的不重做、不重复插入章节。版本已写入但 `report` 未完成时，不得因版本号相等跳过验收。
- 不自动 `git commit` / `push` / 改仓库可见性，不在目标仓库 `git pull`。

## verify

- `inspect` 列出的 from 布局与实态一致；六 Skill / 旧命名 / 新命名 / 已有待办实施都能区分。
- 本跳六项迁移（起点是 1.0.0 时另含上一跳的 `intent-domain`）均为 `applied` 或 `not_applicable`，无 `pending` / `blocked`。
- 目标十 Skill 存在且 `name` 一致；旧名仅以备份形式存在。
- `待办/` `实施/` 目录与 README 在；`进行中/` 业务文件未被批量改派。
- `report.md` 写实际差异、保护内容和验证证据，无私人敏感信息。
- `verify` 通过后，`finalize --apply` 按原 adapter mode 同步候选适配层，candidate check 通过才写 `template_version=1.1.1`，再跑常规 `check`。
- 常规 `check` / `sync` 仍离线可用。
